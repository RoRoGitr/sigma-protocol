# Game development adaptation

Sigma Protocol supports game projects as a conditional adaptation of the existing Steps 0–15 plus conditional 1.5 and 11.5. It does not add a numbered game track.

Set `projectDomain` to `game` in `docs/stack-profile.json`. Missing values remain `general`. Step 1 asks “What are we building?” and records game/general once; a game project defaults to a solo creator until a creator chooses contributor mode.

The canonical catalog selects relevant questions, skills, roles, nested workflows, outputs, review criteria, revision rules, and source references for each existing step. Use selected work on demand. Unknown applicability remains unresolved; a deferral or omission needs a reason.

## Evidence boundary

Protocol and Atlas prepare decisions, briefs, documents, and evidence requirements. They do not perform external game work. A plan is `PREPARED`; asset generation, rendering, rigging, editor imports, playable builds, performance checks, network checks, meter readings, and playtests remain `NOT-EXECUTED` until an authorized external action produces actual evidence and a human reviews it.

Choose the smallest experiment for the current uncertainty. Paper prototypes, outsider testing, blockouts, art freezes, engines, formats, budgets, schedules, and team sizes are not universal requirements. Record why a method applies before making it a gate.

## Collaboration

Contributor idea packs are independently authored and workspace-visible. Explicit synthesis selects exact pack revisions and preserves attribution, agreements, dissent, alternatives, reasons for the selected direction, unresolved questions, and next experiments. It does not grant private access or merge inputs automatically.

## Sources and portability

The catalog carries linked source IDs and evidence status. Skills also include portable source URLs and evaluation briefs under `src/skills/game-*/references/`. Claims distinguish verified source text, observed evidence, source claims, untested integrations, and proposed adaptations. The research interpretation and contract are in [game-development research](research/game-development/).

## Role routing

- `game-design-lead` — player experience, systems, world, and experiment decisions.
- `game-art-director` — visual direction, asset briefs, provenance, and acceptance evidence.
- `game-technical-director` — technical plan, engine/interchange decisions, build evidence requirements.
- `game-quality-lead` — risk-based test and accessibility evidence planning.

These are planning and review roles. They do not imply installed engine access or external execution authority.
