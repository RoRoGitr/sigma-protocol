# Game adaptation — Step 11: PRD Generation

Generated from catalog 1.0.0. Canonical source: `steps/step-11-prd-generation`.

Treatment: **adapt** — Implementation-ready PRDs stay. Each game PRD carries door-problem answers for its interactables, the playtest protocol and evidence grade, accessibility scoping answers, feel or decision metrics, numeric budgets from the tokens and the engine receipt it must produce. Asset PRDs forbid modelling before the reference pack exists and are not closed until the receipt exists. Nested workflow documents are the PRD's inputs.

## Creator questions

- **door-sheets**: Are the door-problem sheets for every interactable in this PRD complete? List unanswered items as hidden scope.
- **acceptance-evidence**: Which receipts, playtest results and performance samples close this PRD, at what evidence grade?
- **budgets**: Which numeric budgets from the design tokens bind this PRD?
- **accessibility**: Which accessibility scoping questions are in scope for this feature and what does each answer require?
- **prerequisite-documents**: Which nested workflow documents must be approved before an agent may start (reference pack, blockout, solution graph)?

## inputs

- FEATURE-BREAKDOWN.md
- Nested workflow documents for the feature
- TECHNICAL-SPEC.md receipt schema
- STATE-SPEC.md

## activities

- Generate PRDs as usual with IDs F<wave>.<feature>
- Inline door-problem answers, playtest protocol, budgets, accessibility answers and receipt requirements
- Block asset PRDs whose prerequisite documents are unapproved
- Run /prd-json --mode implementation afterwards

## reviewCriteria

- An agent could implement without inventing player experience
- Acceptance is a receipt or playtest result, never 'make it fun'
- Prerequisite documents are approved

## revisionRules

- Revising a prerequisite document invalidates the PRD's approval
- A receipt failure re-opens the PRD, not the receipt schema

## Sources and limits

- [The Door Problem](https://web.archive.org/web/20231023231458/https://lizengland.com/blog/2014/04/the-door-problem/) — verified-source-text. Live blog URL returned a stub; Wayback 2023-10-23 and the Kotaku reprint (author-permitted) were used. Essay is an analogy, not a complete spec standard. Large-studio role map does not transfer 1:1 to solo.
- [Xbox Accessibility Guidelines V3.2](https://learn.microsoft.com/en-us/xbox/accessibility/guidelines) — verified-source-text. Official Learn page read (v3.2 published 2023-06-08; page updated 2026-08). Xbox-example-heavy. Explicitly not a legal compliance checklist. Not every guideline body was fully read.
- [Game Design Workshop, 5th Edition - playcentric excerpt](https://www.gamedeveloper.com/design/book-excerpt-game-design-workshop) — verified-source-text. Author-posted excerpt (2024-04-18) read; the full 5th edition was not read cover to cover. Physical prototypes under-serve real-time feel (see S06). Friend playtests bias results (Fulton, in S08).
- [Character - Polycount wiki](http://wiki.polycount.com/wiki/Character) — source-claim. Search extract; URL reconstructed from the page title. Dated community text; adapt for stylised and 2D work.
- [Sigma Protocol game-development adaptation (architecture decision and integration contract)](../SIGMA-GAME-ADAPTATION.md) — proposed-adaptation. Our proposal, not an external practitioner method. Nothing here proves a game is good. Every phase's evidence must come from an authorized external experiment and a human review, never from the existence of a document.
