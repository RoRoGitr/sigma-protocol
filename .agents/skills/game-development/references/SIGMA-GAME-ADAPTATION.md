# Decision: one planning journey with a game domain adaptation

Status: adopted for this authorized local implementation, 2026-09-22. Owner: Audit and update Sigma Protocol, including Atlas after Dallion’s explicit “you handle it all.” This is an architectural decision, not a claim that the integration is built or any game is validated.

## Options

| Choice | Benefits | Costs and decision |
| --- | --- | --- |
| Separate numbered game track | Familiar game-production vocabulary in a standalone sequence | Duplicates gates, context, team/company ownership and exports; risks losing operations and breaking existing numeric contracts. Rejected for this commission. |
| Domain adaptation of existing steps | Keeps the complete product/company system, artifact revision model and existing projects; adds game methods where applicable | Needs explicit Protocol-to-Atlas mapping and context/validator parity. Selected. |

Protocol retains Steps 0–15 plus conditional 1.5 and 11.5. Atlas retains all twenty stages: its 11 includes Protocol 11/11.5; 12–14 are operating-company extensions; 15–18 map to Protocol 12–15. Company domains/functions and a project’s game classification are distinct.

## Research interpretation

Fullerton’s playcentric approach and MDA support experience goals, testable mechanics and iteration, not a paperwork-only waterfall. The Level Design Book distinguishes blockout-led combat/spatial work from story/art-dependent cases. Therefore a physical prototype, outsider test, fixed pillar count, art freeze or particular engine is not a universal entry requirement. Choose the smallest experiment that can test the actual uncertainty; record unknowns and revisit conditions.

The Grok reports are inputs. Their “demonstrated” label for inspected text is normalized to **verified source text**, distinct from observed footage, source claims, untested integrations and our proposed adaptations. Reading a PDF is not a demonstrated runtime result. Source-specific techniques are attributed without copying a proprietary curriculum or treating practitioner prominence as a ranking.

## Integration constraints

- Optional projectDomain general/game; missing means general. New/existing project mode and company role-sharing teamMode keep their existing meanings.
- Solo is the default. Optional creator mode and contributor idea packs do not grant user accounts or private access controls. Packs are independently authored and workspace-visible.
- One versioned canonical domain catalog supplies all step mappings, questions, nested workflow phases, outputs, source references, roles and review/revision rules. Atlas consumes a pinned repository-local copy; no dependency on the author’s machine paths.
- Nested workflow phases, creator profiles, idea packs and synthesis are recognized JSON documents inside ordinary project artifacts. Existing envelope ownership, functions, dependsOn, history, reviews and invalidation remain authoritative. Do not add parallel workflow state stores.
- Instantiate selected work on demand. Unknown applicability is unresolved; skipping/deferment requires a reason. Do not pre-create every optional template and then mistake the resulting blockers for required scope.
- Synthesis explicitly selects idea-pack revisions, retains attribution/dissent/rejected alternatives, and depends on those artifacts. No automatic merger or claim that hidden inputs were read. Planner context excerpts disclose limits; no synthesis from silently truncated inputs.
- Game metadata and method context must reach browser and Rust planners, storage validation, transfer/import and readable handoffs. Legacy non-game records remain valid.
- Atlas only prepares briefs, decisions, documents and evidence requirements. External Blender/engine work is separate: proposed experiment → authorized execution elsewhere → actual evidence → human review. Render, rig, engine import, playable build, performance and multiplayer proofs remain distinct.

## Acceptance

Create/resume a game project; receive game-appropriate questions; enter character/environment/level nested phases; save reviewed planning artifacts; create independent idea packs and explicit synthesis; edit an input and observe dependent review invalidation; retain company functions/owners/GTM/ops; export and reimport an honest execution package. Verify a legacy general project, solo default, optional team mode, stale/foreign inputs, invalid templates, conditional scope and no implicit external execution.
