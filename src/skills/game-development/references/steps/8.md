# Game adaptation — Step 8: Technical Spec

Generated from catalog 1.0.0. Canonical source: `steps/step-8-technical-spec`.

Treatment: **adapt** — The implementation blueprint stays. For a game it names the engine (if now decided), interchange formats and their known losses, the skeleton or sprite-rig contract, sidecar schema for provenance and budgets, input matrix, save schema with migration, audio bus architecture, accessibility APIs, streaming and collision policy, the test ladder and the engine-receipt schema that closes asset PRDs. Multiplayer and entitlement sections are conditional on earlier answers.

## Creator questions

- **interchange**: Which interchange format(s) carry assets into the engine, and which data are known to be lost or transformed (vertex splits, bone influence caps, UDIM tiles, unsupported nodes)?
- **skeleton-contract**: Is there a shared skeleton or 2D rig contract (engine mannequin, custom, none)? What retarget cost experiment justified it?
- **sidecar-schema**: What fields does every asset's provenance sidecar carry (license, creator, source, AI generation, LOD and collision policy, budgets, engine and DCC minimum versions)?
- **test-ladder**: What are the rungs of the test ladder from asset validation through package and soak, and which are automated?
- **receipt-schema**: What does an engine receipt contain for an asset or level to count as done (import log, three-way comparison, contact-set playback, performance sample, sidecar copy)?
- **input-save-audio**: Specify the input matrix, the save schema and migration rule, and the audio bus list.

## revisionRules

- Engine or version change re-opens interchange, receipt and test-ladder sections
- A receipt failure in any asset phase re-opens the receipt schema only if the schema was wrong, otherwise the asset
