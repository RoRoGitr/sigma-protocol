# Game adaptation — Step 9: Landing Page

Generated from catalog 1.0.0. Canonical source: `steps/step-9-landing-page`.

Treatment: **conditional** — Optional in the Protocol and still optional here. For games the landing surface is usually a store page, trailer and demo or playtest policy. Copy restates experience goals; it may not name unproven systems. Coming-soon pages and wishlists wait until a playable slice exists and the goals still hold. Accessibility tags must match shipped options.

## Creator questions

- **store-surface**: Where will players first meet the game (storefront page, web page, itch page, physical booth, none yet)?
- **copy-from-goals**: Write the description from experience goals only. Which sentences could not be written without naming an unproven system?
- **playtest-policy**: Public playtest, closed keys, demo, or nothing yet? What leak risk is accepted?
- **tag-honesty**: Which accessibility or feature tags will be claimed, and which shipped option backs each?

## inputs

- Experience-goal sheet
- Playable slice evidence
- Distribution class and offer decision

## activities

- Run the standard landing-page strategy when a page is wanted
- Draft store copy from the goals and run the store-page lie test
- Choose the playtest and demo policy against the storefront's rules
- Plan the capture pipeline for trailers with the same provenance rules as assets

## Sources and limits

PC-storefront specific. Leak risk for unannounced games. Wishlist non-interference is Valve's claim, not measured here.

- [Sigma Protocol game-development adaptation (architecture decision and integration contract)](../SIGMA-GAME-ADAPTATION.md) — proposed-adaptation. Our proposal, not an external practitioner method. Nothing here proves a game is good. Every phase's evidence must come from an authorized external experiment and a human review, never from the existence of a document.
